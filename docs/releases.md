# 版本与发布

用户已于 2026-10-13 授权：以当前网站发布 `v1.0.0`；此后每次要求更新网站，完成并验证后，自动变更版本号、部署阿里云并发布 GitHub Release。这是执行网站更新时的持续约定，不是后台定时任务。

线上网站：<https://mumao.site/>。源码及发布记录：<https://github.com/Mumao233/personal-web>。

## 版本规则

| 改动 | 升版方式 | 从 1.0.0 出发的示例 |
| --- | --- | --- |
| 缺陷修复、兼容现有行为的细节调整、文档更新 | 补丁版本 | 1.0.1 |
| 新功能或兼容现有内容的功能增强 | 次版本，补丁归零 | 1.1.0 |
| 不兼容的行为、接口或数据格式改变 | 主版本，其余归零 | 2.0.0 |

一次已完成的更新集中发布一个版本；处理中不因每次编辑、提交或测试单独升版。用户指定版本号或明确要求暂缓发布时，以当次指示为准。只回答问题、未修改网站，或工作尚未完成时，不创建空发布。

`package.json`、`package-lock.json` 的项目版本、`README.md` 的当前版本、`CHANGELOG.md`、Git 标签 `v<版本号>`、GitHub Release 与服务器 `release.json` 的版本必须一致。发布清单同时记录实际部署的提交和验证结果；不要将未运行的检查记为通过。

## 每次更新的完成流程

1. **实现与验证。** 完成用户要求，运行与改动相关的测试和生产构建；涉及交互、布局或发布流程时，用隔离数据进行浏览器验收。保留旧内容兼容性，修复失败后再发布。
2. **确定版本。** 按上述规则更新 `package.json` 和锁文件，在 `CHANGELOG.md` 记录日期、用户可感知的变化及必要限制。先检查远端标签与发布记录，避免重名。
3. **提交源码。** 检查变更范围和 Git 状态，排除凭据、数据库、上传文件、测试数据和运行缓存。提交本次更新，明确对应的 Git 提交；依当前仓库约定推送到 `origin/main`。
4. **备份与部署。** 参考 [阿里云部署记录](../deploy/README.md)，在服务器做 SQLite 一致性备份并备份上传文件，保留旧应用以便回滚。构建并部署本次提交，写入包含版本号和提交的 `release.json`。持久数据继续使用 `/opt/personal-web/data`，不可用本地数据库或测试数据覆盖。
5. **验收线上版本。** 确认服务运行、HTTPS 首页与太阳系可访问、健康接口正常，以及本次改变的关键路径正常。核对服务器发布清单与本地提交；涉及持久数据时检查内容保留情况。
6. **发布版本。** 为已验收的准确提交创建附注标签 `v<版本号>` 并推送，创建同名 GitHub Release，使用更新记录整理发布说明。源码归档由 GitHub 提供；如附加部署包，先确认不含私人数据和凭据。
7. **确认结果。** 核验远端提交、标签指向和 GitHub Release；向用户提供版本号、网站与 Release 链接，以及仍未解决的限制。

同一版本的标签和 Release 不得覆盖或移动。发现已发布版本的问题，应修复后发布新版本。部署或发布失败时保留可追溯状态，按需要恢复旧应用，明确告知尚未完成的环节；不能只改版本文件就宣称发布成功。

日常升版、Git 推送、部署和创建 Release 已获用户授权，无需反复确认。涉及新的破坏性操作或授权范围外事项时，单独处理；不要为普通发布另设审批步骤。

## 数据与回滚

- 数据库、照片上传及凭据不提交 Git，不进入 Release 附件。
- 数据迁移前保留一致性备份，优先采用可兼容旧内容的迁移方式。
- 应用回滚恢复上一份应用代码；除非明确需要回滚用户内容，不恢复旧数据库，以免丢失部署后新增的数据。
- 阿里云实例、路径、服务配置与已有回滚方法以 [部署记录](../deploy/README.md) 为准；执行前核对当前环境，勿直接沿用过期状态。
